## 23/11/2026 -- custom Vulkan driver manager: per-GPU catalogue, in-app download, revert after failed starts

The driver card used to be Adreno-only, hidden behind the experimental Vulkan unlock, and
the only way to get a driver in was to import a zip by hand. The manager is now a real
feature: `SetupActivity` builds a card that is always visible, `GpuInfo` reads the GPU from
`GL_RENDERER` and filters a catalogue of eleven community sources by family -- Turnip builds
(ARMSX2, K11MCH1, MrPurple, Banners, Droid-Deck) and StevenMXZ Gen8 for Adreno, MaliSX2 for
Mali G31-G715, ExynosTools and MdiEx for Xclipse -- and `DriverDownload` fetches the newest
release asset from GitHub, checks its SHA-256, and installs the adrenotools-format zip. The
card shows the recommended driver for the phone and the credit line under each download
button, because these are other people's open-source work, not ours.

The safety net counts failed starts and reverts to the system driver after two. The first
version counted every launch, which punished GLES players for crashes that had nothing to
do with the driver; it now counts Vulkan launches only, and a GLES launch clears the
counter. One design note from the ARMSX2 study that shaped this: pin the driver before the
first Vulkan load, and always keep a working fallback -- the revert path is the feature,
not the download.

## 23/11/2026 -- Mali phones default to Quality upscaling; 60 Hz sim gets a warning

Two small fixes that came out of the same device session. On a Mali phone the default
upscaler was Performance (50%), which is cheaper than the phone needs; Mali now defaults
to Quality (67%) unless the player already picked a mode, seeded into `Options.ini` when
the Graphics tab is built and again on game launch. On the old Mali test phone that moved
44 to 57 fps at 75% with GSR, interface still at full resolution.

The other one is a warning, not a fix: a 60 Hz sim rate on Mali doubles the logic work on
a CPU-bound phone, and the sim-rate picker gave no hint of that. It now shows a warning
with a one-tap "Use 30 Hz" button when Mali is detected. The 9 fps report that prompted
it (sim 60 Hz, Game Speed slider at 20, bracket [40]) is the same story: 9/60 is 15% of
real-time speed, where 28/30 is 93%.

## 23/11/2026 -- driver download always failed: the credit line was read as a checksum

A device test caught it: tapping Download MaliSX2 always toasted "Checksum mismatch".
The 6-argument `DriverCatalog.Source` constructor took its last parameter as a pinned
SHA-256, so the nine sources that passed a credit line there compared every downloaded
zip against that text and always failed -- and showed no credit under their buttons.
The 6th argument is now the credit; a pinned checksum uses the 9-argument form
(`aa92761`). MaliSX2 itself has no pinned checksum by design (empty means skip the
check). The failed download changed nothing on disk, so the manually imported MaliSX2
0.6.1 was untouched. The credit line now shows on the card, which is how the fix was
confirmed on device.

## 23/11/2026 -- the in-game bottleneck is the per-frame terrain update, not the GPU

The investigation (engine thread, not GPU/sim/pixels) ranked three suspects. First,
the phase logged as `preRTT` is not the render-to-texture passes -- in
`W3DDisplay::draw()` it is `updateViews()` plus the particle update, and it grows
across the session: 91 -> 122 -> 132 -> 177 ms, while the main scene stays flat at
12-20 ms. Inside it the prime suspect is the terrain-center recompute
(`W3DView::update()` -> `updateTerrain()` -> `HeightMap::updateCenter()` ->
`updateBlock()` -> `updateVB()`): the upload volume tracks it almost exactly
(91 ms with 23 MB, 122 ms with 35 MB). Particle counts are tiny (14-16 draws), so the
particle update is unlikely to be 90 ms -- but that is an inference, not a measurement,
and the zoom-settle path (`adjustZoomWhenNotScrolling` keeping `m_recalcCamera` set)
is an unproven candidate for why it never goes quiet.

Second, plain-lock vertex uploads: 23-35 MB/frame across 173-259 uploads. The dynamic
ring buffer is innocent (DISCARD/NOOVERWRITE, 0.04 ms); the plain locks come from
`HeightMapRenderObjClass::updateVB`, which locks the whole 180 KB tile buffer per
touched tile though only a few rows changed. The attribution is not complete: 23-35 MB
is 128-192 tile-equivalents against 16-64 visible tiles, so another plain-lock user
may contribute.

Third, the 1044 terrain draws per frame are mostly a red herring: 1.3-2.7 ms of
translator time and 0.1 ms of `glDraw`. Three passes per tile is the fixed shader model
(base + noise + cloud), not a bug. Ruled out by the log: logic, pixels, water/shadow
RTT (0.00 ms in every window), UI, models/particles/decals, audio, network, present,
and GPU saturation (render worker busy 20-27 ms against 126-217 ms frames). The 1.8 fps
window partly overlapped the map-load hitch, so steady state is ~6-7 fps -- still bad.

The recommended order: (1) a diagnostic build that splits the update phase and tags
uploads by source; (2) ranged terrain VB locks (upload only the touched rows);
(3) terrain-center throttling / zoom-settle fix, guided by the diagnostic; (4) merge
the 3 terrain passes and re-run terrain LOD calibration on game start. If the update
phase drops from ~130 ms to ~20 ms that is roughly 3x fps on its own; ranged locks
should take another 20-30 ms off the frame.

Build 10409 (`bce9374`) is that diagnostic build: `[GX-PERF-DISPLAY]` gains
`updViews` and `particles`, a new `[GX-PERF-VIEW]` line reports `view` / `terrain` /
`terrainCalls` / `rest` / `centerCalls` / `blockCalls` / `blockCells` once per second,
and a new `[d3d8gles] perf-syncupload/frame by source` line splits synchronized
uploads into terrain / models / sorted / 2d-ui / other. Measurement only. The next
device log (skirmish, 1 minute or more) settles suspects 1 and 2 together.

## 23/11/2026 -- Beta 10411 black 3D view: pitch hysteresis, cheap resize, diagnostics that measure

Beta 10411 (head `d3765f6`) rendered the in-game 3D view uniformly black --
UI, command bar and minimap fine, game running at 14 fps. The 1.0.0 build
did not do this. The device log from the static-camera test names the
trigger: `[GX-PERF-GATE]` shows `sizeChg` exactly equal to `full` (831
each) over the session, so every single `updateTerrain()` call was a forced
full update with a draw-size change, while the camera did not move
(`changed=1`, `posDMax=0.00`, `rotDMax=0.0000`).

The cause is the 37-degree pitch threshold. The default camera pitch is
37.5 degrees, half a degree above it, and the pitch wobbles by a hair
every frame (camera settle and area-constraint clips nudge the transform),
so a still camera crossed the threshold on every call. Each crossing ran
`setTerrainDrawSize()` -> `initHeightData()`: free and re-create every
terrain vertex buffer tile, reset the shroud, rewrite all 159,201 cells
with null lights, and set the full-update flag. The flag was never
cleared, because `updateCenter()` early-returns when the draw window
covers the whole map -- before the branch that clears it -- so
`W3DView::update()` called `updateTerrain()` a second time every frame
and the rebuild ran twice a frame. The terrain draws were still submitted
(693/frame) and the uploads still happened (~20 MB/frame), so the
geometry reached the GPU but came out black. The epsilon gate is
innocent -- it never skips in-game (`skip=0`). The null lights are
innocent too (`doTheLight` still applies the ambient and the sun with a
null iterator), and the shroud is not it either (its reveal runs
synchronously in init, and this build has no fog interpolation). What the
log alone cannot pin down is which single GPU-side effect of the
per-frame rebuild turns the output black -- the d3d8gles command ring
serializes the buffer deletes and draws in order, so it is not a plain
race. The rebuild itself is the trigger: 1.0.0's sessions never rebuilt
per frame and rendered fine.

Three changes, same commit. (1) Pitch hysteresis in `updateTerrain()`:
the size now drops to the low-angle band below 36 degrees and comes back
to normal above 38 -- a 2-degree dead band around the 37-degree
threshold, several times wider than the sub-degree wobble, so a still
camera can never flip the size; a real pitch change still switches
promptly. The first update picks the band from the plain threshold.
(2) A resize is cheap when it can be: if the new size fits the tile grid
already allocated (same tile counts -- the grid's row stride is baked
into the tile and backup arrays, so a grid change genuinely needs the
rebuild), `setTerrainDrawSize()` just records the new size and flags a
full update, and `updateCenter()` rewrites the window with the real
lights -- no buffer reallocation, no shroud reset. A band change still
takes the full rebuild, but only once. (3) `updateCenter()` now consumes
a pending full update before its early return (rewrite with real lights,
clear the flag) and samples the pitch there too, so the `[GX-PERF-GATE]`
pitch range and branch counts finally measure in-game instead of staying
0.0..0.0. The gate itself is untouched, and so are the `[GX-PERF-GATE]` /
`[GX-PERF-VIEW]` formats.

Known costs: a band change still costs two full rewrites in one frame
(`initHeightData` with null lights, then `updateCenter` with real
lights) -- rare, and correct. The exact GPU-side failure is not proven
from the log alone; the on-device test is the proof.

What the next device log needs to show: the 3D view visible again, then
the static-camera test (~30 s still, ~1 min normal play, GLES):
`[GX-PERF-GATE]` `sizeChg` near 0, `skip` climbing when the camera is
still, `cFull` counting at most one per resize, `pitchDeg` showing the
real range; `[GX-PERF-VIEW]` `view` and `blockCells` falling once the
camera stops.

## 23/11/2026 -- Beta 10412: the draw size still flips every frame -- it was never the pitch

The black screen is gone in 10412 and quiet moments run 33-38 fps, but
active play still has bursts where the terrain rewrites fully every frame
(`[GX-PERF-VIEW]` view 77-163 ms, `blockCells` 318,402, fps dipping to
12-17) with the camera still. The `[GX-PERF-GATE]` totals say it plainly:
`sizeChg=359` exactly equals `full=359` -- every full update is a size
change, and the pitch the diagnostic measures is a steady 38.0..38.0 in
every active window. So the hysteresis (low below 36 degrees, back to
normal above 38) cannot be the problem: a pitch that never moves cannot
cross a 2-degree dead band, and the band state latches after the first
update -- it is never reset anywhere.

The real driver is a second writer of the stored draw size.
`updateTerrain()` asks `setTerrainDrawSize()` for a size (low band 257 x
draw-distance scale, clamped to the map -- 400x400 on this device), which
stores it. Then `updateCenter()` calls `setDrawArea()` with the area from
`WorldHeightMap::createDrawArea()`, and that function replaced the stored
size with the stretch size (65x65) when `m_stretchTerrain` is set, or with
the whole map when `m_drawEntireTerrain` is set -- either flag is enough.
The next `updateTerrain()` then sees the stored size differ from the one
it asked for and "changes" it again. Every frame: request 400, store 400,
overwrite to 65 (or the map size), request 400 again. The pitch never
moves, the band never flips, and the size still changes on every update.
The numbers fit exactly: each rewrite is 399x399 cells, the 400 that
`updateTerrain()` asked for, and `blockCalls` 2.0 per update is the two
rewrites (one from `initHeightData` on the size change, one from
`updateCenter`'s full branch). One of the two flags has to be set on the
device -- both default to false in `GlobalData`, so it comes from the
mod's `GameData.ini` -- but which one does not matter for the fix.

Two changes, same commit. (1) `createDrawArea()` no longer replaces the
size: the draw area is the stored size, clamped to the map, with the
origin clamped into the map. The stored size has a single owner now,
`setTerrainDrawSize()`. The flags still take effect where they belong --
the far clip plane and the tree panels read them directly, and the origin
clamping here still uses the real window size, which is what the shroud,
the draw region and the shadow edge want too. The grid itself never
changed with the flags (it is set by `setTerrainDrawSize()` from
`updateTerrain()`'s request, which never asks for the stretch size), so
nothing the player sees changes -- the terrain just stops being rebuilt
every frame. (2) A new `[GX-DRAWSIZE]` line, printed only when the stored
size actually changes, logs the pitch to three decimals, the band, the
requested and the previously stored size, both flags, the draw-distance
scale and the map extent -- so the next log names the culprit if the size
ever changes again. When the size is stable the line stays silent. The
`[GX-PERF-GATE]` / `[GX-PERF-VIEW]` formats are untouched, and so are the
epsilon gate and the hysteresis.

One loose end from the same log: `m_recalcCamera` is set on every frame
even with no mover active (zoom and pivot are settled, `zoomSet=0`,
`pivotSet=0`), so `updateTerrain()` still runs once per frame -- that is
what lets the flip happen at all. The only setter left in the settled
path is the area-constraint clip in `updateCameraAreaConstraints()`: the
camera sits on a constraint boundary and gets clipped (or re-checked)
every frame. Left alone on purpose -- after this fix each of those runs
is a cheap no-op (`setTerrainDrawSize()` returns early, the gate skips
`updateCenter()`), and changing the clip risks camera behaviour. If the
next log still shows `recalc` at 1.0 per frame, that is expected; what
matters is `sizeChg` and `view`.

What the next device log needs to show: static-camera ~30 s + normal
play ~1 min, GLES: `[GX-PERF-GATE]` `sizeChg` near 0 during still-camera
play, `[GX-PERF-VIEW]` `view` staying low (single digits, not 77-163 ms)
and `blockCells` near 0 when the camera stops, `[gxfps]` no longer
dipping to 12-17. No `[GX-DRAWSIZE]` line at all means the size never
changed; one with `was=65x65` and `stretch=1` (or `was` equal to the map
size with `entire=1`) would mean the overwrite is still happening
somewhere and this fix missed a writer.

## 23/11/2026 -- Beta 10413 crash: a wild weapon-template pointer, and a crash log that will name the next shot

Build 10413 ran ~23 minutes at the 40 fps cap and then crashed: segfault,
fault address 0x37, in AsciiString's copy constructor, called from
Weapon::newProjectileFired. The disassembly of the shipped libmain.so
proved the fault is not the string: Weapon::m_template was 0x17, a wild
pointer, not null -- the copy constructor loads the template's
projectile-stream name at offset 0x20, so 0x37 - 0x20 = 0x17. The template
was still valid when privateFireWeapon started and through
fireWeaponTemplate's early reads (the projectile was created fine), so it
goes bad somewhere between getProjectileTemplate and newProjectileFired:
projectile creation, setProducer, battle-plan bonuses, or a script call.
The exact writer is not identified, and a null guard would not have
caught 0x17, so no speculative fix was committed.

Two changes instead, same commit. (1) A null guard in newProjectileFired,
matching the one at privateFireWeapon entry -- hardening only, and the
comment says so plainly: it does not fix the 10413 crash. (2) A diagnostic
that will identify the writer on the next occurrence: fireWeaponTemplate
now records every shot -- frame, firing unit's template name, weapon
template name, projectile-stream name, and whether the target is an object
or a ground position -- into one pre-formatted line in a fixed 512-byte
buffer (one snprintf per shot, no heap allocation, AsciiString copies only
bump a refcount). The crash handler prints that line first in crash.log,
as `[GX-CRASH] last fired: ...`, via the same weak-reference pattern the
GLES context already uses. The handler reads the buffer with a bounded
scan, so a crash on another thread landing mid-write can only garble the
line, never overrun it. Silent in normal play -- nothing is logged per
shot, only the crash-handler line.

What the next device log needs to show: if the game crashes again while a
deployed turret is firing, crash.log should carry the `[GX-CRASH]` line
naming the unit and weapon -- that, plus which unit was firing and what it
was shooting at, is what pins down the writer.

## 23/11/2026 -- Beta 10414 crash: the DF-41 names the writer -- a weapon set rebuilt mid-shot

Build 10414 crashed the same way as 10413, and this time the diagnostic
worked: crash.log carries `[GX-CRASH] last fired: frame=57250
unit='China_VehicleDF41' weapon='DF41MissileWeapon' stream=''
target=ground(2265,309,49)`. A deployed DF-41 missile launcher firing at
a ground position, after only ~60 seconds of play -- the crash reproduces
fast with this unit. The empty stream name is a red herring: the copy in
newProjectileFired happens before the empty check, so an empty stream
changes nothing about the crash.

Verified against the shipped run19 binary (symbols
libmain-run19.symbols.txt.gz, BuildID matches the crash): m_template is
0x17 again, same value as 10413. The null guard from the last commit is
in the binary and correctly passes 0x17, so it never had a chance. The
firing Weapon pointer itself is intact -- it is the Weapon object's
m_template field that holds 0x17.

The mechanism, traced through the disassembly and the source: creating
the projectile can rebuild the firer's weapon set while the shot is still
in flight. The projectile's onCreate may grant a player upgrade
(GrantUpgradeCreate), and Player::addUpgrade runs updateUpgradeModules on
every object of that player, so a WeaponSetUpgrade on the firer sets
WEAPONSET_PLAYER_UPGRADE and calls updateWeaponSet, which deletes the
firing Weapon and builds a fresh one. The firingWeapon pointer held by
fireWeaponTemplate is then a freed heap block. Two things that made the
earlier investigation rule this out turned out to be wrong for this build:
Weapons are not pool-allocated -- this build uses GameMemoryNull.h, so
newInstance is plain new and the binary allocates Weapons with malloc --
so a freed Weapon block can be reused by any heap object, not only by
another Weapon. And the script call in the window does not run script
code at all: notifyScriptEngine only enqueues the completed power for
later. setProducer, the battle-plan bonuses, and the die notification
were all checked in the binary and do not touch the firer's Weapon.

What is 0x17? In this build's numbering it is KINDOF_PRELOAD (23), and
it could also be an ObjectID or a count. Which heap object wrote it is
not proven -- that needs the mod's data. The trigger itself is also not
yet confirmed from the .big files: it needs a GrantUpgradeCreate
(player-type) on the DF-41 missile projectile, or on an object the
weapon's FireOCL creates, plus a WeaponSetUpgrade on the DF-41 itself.
Both live in the TEOD mod's INI, not in this repo. The grant only fires
once per game (updateUpgradeModules skips modules that are already
upgraded), which fits the crash being rare and tied to this one unit.

The fix, same commit: stop holding a Weapon pointer across the
projectile creation. fireWeaponTemplate re-fetches the weapon now in
the slot right before newProjectileFired -- if the set was rebuilt that
is the new weapon, otherwise it is the same one, so nothing changes;
if the slot is empty the stream is simply not recorded. Both
Object::fireCurrentWeapon overloads do the same before calling the
firing tracker, remembering the slot before the shot and re-fetching
after it. Known follow-up, not done here: Weapon::privateFireWeapon
still does its ammo and cooldown bookkeeping on `this` after
fireWeaponTemplate returns. The freed block is normally reused by the
new Weapon allocated in the same rebuild, so those writes land on a
valid Weapon, but the tail should be re-fetched the same way when
someone next touches that function.

Test on device: a fresh game, DF-41, attack-ground. If it no longer
crashes on the first shot, the fix holds. Also worth checking whether
other deployed missile units crash the same way -- if only the DF-41
does, the trigger is its own INI, not the firing path in general.

from Weapon::newProjectileFired, DF-41 firing attack-ground, ~55 seconds
into a fresh game. The run20 binary (BuildID d91f85d6, symbols from the
beta release) proves why the re-fetch did not save it. The re-fetch is
in the binary -- fireWeaponTemplate calls getWeaponInWeaponSlot and then
does `csel x0, x28, x0, eq`, keeping the OLD firingWeapon when the slot
comes back null -- and m_template is 0x17 again (copy ctor +0xc is
`ldr x8, [x1]` with x1 = 0x37; newProjectileFired loads m_template at
+0x10 and adds 0x20 for the stream name). The Weapon is valid at
privateFireWeapon entry -- its m_template reads there would fault first
otherwise -- and updateWeaponSet is the only mid-shot path that deletes
slot weapons (the only other deleteInstance(m_weapons[i]) is the
WeaponSet destructor, which only runs when the object dies). So the
crash can only have happened one way: the rebuilt set has no weapon in
the firing slot, the re-fetch returned null, and the code fell back to
the freed pointer anyway. The 23/11 diary entry even said "if the slot
is empty the stream is simply not recorded" -- but the code never
skipped the call in that case.

The fix, same commit: when the re-fetch returns null, set firingWeapon
to null so newProjectileFired is skipped. The projectile itself is
unaffected -- it was already created and is launched below; only the
stream notification is skipped, and there is no weapon to report one
for. This is safe no matter which hypothesis is right: if the slot is
empty, the old code crashed anyway.

The commit also extends the crash diagnostic, so the next crash settles
which pointer went bad and when. A second crash-log line now records
the raw pointers: the Weapon and its template at fireWeaponTemplate
entry, and again right before newProjectileFired -- the old pointer and
its template, plus the re-fetched pointer, its template, and whether
the slot came back empty. Reading a template pointer out of a Weapon
is only a field load, never a dereference, so it is safe even on a
freed block. If the next crash shows slotEmpty=1 with oldWpnTmpl=0x17,
the empty-slot story is confirmed and the skip above should have
caught it; if it shows the re-fetched pointer equal to the entry
pointer with a wild template, the corruption is in place and the
writer is elsewhere. There is no second newProjectileFired call site
in fireWeaponTemplate, and nothing runs between the re-fetch and the
call, so those two readings cover the whole window.

Build 10416 crashed again, but the crash moved -- the 4bda4cc skip
worked for its target. It is no longer in newProjectileFired. It is in
Weapon::privateFireWeapon+0x364, the tail that does ammo and cooldown
bookkeeping on `this` after fireWeaponTemplate returns, which the
23/11 entry left alone as "low risk". The run21 binary (BuildID
f9450dbc, symbols from the beta release) proves what that offset
touches: `ldr w9, [x10, #0x250]` where x10 is m_template, loaded from
[this+0x10] -- m_template->getShotsPerBarrel(), in the barrel-advance
block after --m_numShotsForCurBarrel reaches zero. With m_template the
wild 0x17 the crash log showed, 0x17+0x250 is exactly the fault address
0x267. ShotsPerBarrel defaults to 1, so a DF-41 shot takes this path
every time. The plain field writes before it (ammo, barrel, last fire
frame) did not fault only because the freed block is still mapped
memory; they wrote into whatever reused it. The "low risk" call was
wrong for a different reason than expected: it assumed the freed block
would be reused by a new Weapon, but the rebuilt set has no weapon in
this slot, so nothing reallocated the block at all.

The fix, same commit: privateFireWeapon captures the slot in a local
before firing and, once fireWeaponTemplate returns, checks the slot
still holds this Weapon. If it does not -- empty slot, or a fresh
Weapon in its place -- the tail is skipped and the function returns
false, which is honest: no reload happened. The slot is captured
before the shot, not read after it, because reading m_wslot out of a
freed Weapon would itself be a use-after-free. If the freed block was
reused by a new Weapon at the same address, the check passes and the
tail runs on a valid Weapon. Weapon::fireWeapon itself needs nothing:
both overloads just return privateFireWeapon, so the one check covers
the whole remainder. The new weapon in the slot, if any, stays fresh
and ready to fire -- it has not fired, so there is no cooldown to
carry over. The DF-41 INI trigger is still unconfirmed, and the fix
does not depend on it.

Same build, a new report from the same session: a new game starts on
a black 3D view until the zoom is just right. The log rules out the
10411 mechanism -- sizeChg=2, full=3, both at map loads, pitch steady
at 38.0 in the normal band -- and the terrain itself is drawn the whole
time: 330 draws a frame on the 440x440 map, 240 on the 170x320 one, from
shortly after each map load. So the black is not missing geometry. Two
things can make drawn terrain look black. The first is the shroud: the
shroud pass multiplies the terrain, and unexplored ground multiplies to
black. At game start almost everything is unexplored, and the camera
starts at max zoom, which on this 2.22-aspect screen sits about 1.9x

the tester had to do. The second is the draw window: the 258x258 window
is centered on the visible region, and the visible ground region at max

moved into the size request: the window is not the main cause at

The commit adds one diagnostic instead of a speculative fix. On every

faster: lit terrain under the base means shroud, the base floating on

Build 10417 holds the crash fix and confirms the black screen, but the

all in the log (crash.log has only the load header), so the DF-41
fire-tail fix holds. On a new game the frame time grows monotonically,
68.8 ms to 4021.5 ms over about two minutes, fps 14.5 down to 0.2, and
then instantly recovers to 27-30 fps on the next map. The smoking gun
is one [GX-PERF] line: frames=1 avgFrameMs=4195.68 with logic=2080.28
ms and client 5.88 ms -- a single logic step taking two seconds. The
renderer is proven innocent in the same log: view max 2.76 ms, present

throttling is in the log (CPUs down to 1260/910 and 1150/650 MHz at
times) but it does not explain a smooth monotonic growth that resets
instantly on a map change.

Two things were ruled out by reading the code. Pathfinding is capped:
processPathfindQueue stops at PATHFIND_CELLS_PER_FRAME (5000 cells) a
frame, and one A* search stops at the same cap, so it cannot be a
2-second step on its own -- and the queue only ever grows if requests
arrive faster than the budget, which the next log can now show. The
shroud full refresh is not in the logic path either: it runs at map
init, on load, and from the render-side shroud code, never per logic
frame, and its cost is fixed by the cell count anyway. The catch-up
speed-up from 02/10 is an amplifier, not the cause: at the 40 fps cap
it runs one extra logic step a frame (speedCatchUpSteps=1), so the
4195 ms frame is 2080 + 2080 + client. The step itself is the problem;
the catch-up only doubles it.

So this commit adds a diagnostic instead of a speculative fix, and one
small safe fix. [GX-PERF-LOGIC] splits one logic step per subsystem,
once a second: script, terrain, CRC, stats, recorder, commands, normal
updates, sleepy updates, AI, build assistant, partition, destroy list
and stores, disabled-status scan -- average and worst per call, plus
the object count, so the next log can tell whether the cost tracks the
number of objects. [GX-PERF-AI] splits the AI step further into the
pathfinder queue and the player updates. Both are measurement only,
gated by the same perf flag as [GX-PERF]. The fix is the catch-up cap
the 02/10 comment already promised in spirit: if the regular step just
ran longer than one frame interval, the game is behind because the
simulation itself is slow, so the extra steps are skipped and the debt
is dropped. Same steps in the same order, so replays and saves are
unaffected; when the game is keeping up, nothing changes. It halves the
worst frame (4195 ms becomes ~2080 ms) but it does not fix the
collapse -- the 2-second step is still there, and the next log has to
name it.

## 24/11/2026 -- Stop re-testing a collision pair every frame when neither object moved

The 10418 log named the hotspot: the `part` phase -- ThePartitionManager->UPDATE()
-- cost 1138.75 ms in one logic step at obj=1695, while a calm game with the
same object count costs 3-12 ms. The cause is in
PartitionContactList::processContactList(): after every real collision, both
objects are re-dirtied with makeDirty(false), so the next frame's update()
gathers the same pair again, tests it again, and re-dirties it again. In a
dense battle that loop is quadratic and self-sustaining.

The fix only re-dirties an object when the collision changed something a
re-test could see: either it has a non-physics collide module, or the push
actually moved it. Each object's position is snapshotted before the onCollide
calls and compared after, with the same 0.01 world-unit threshold
Object::isPosDifferent() uses -- PhysicsBehavior jitters a standing-still
object by roundoff amounts, and the engine itself treats a move below that
as no move at all, so the skip and the movement path agree. A real move is
already re-checked through the movement path (a position change dirties the
partition with a full cell update), so skipping this re-dirty loses no
collision. Objects with a non-physics collide module keep the old behaviour:
FireWeaponCollide fires its weapon every frame by design, and SquishCollide,
Minefield, Crate, POWTruck, the contain modules and Railroad are one-shot or
movement-driven events, so they are not touched by the skip. The existing
guards are unchanged -- destroyed, no partition data, or immobile objects are
never re-dirtied -- and the skip is per object, so a pair is only fully quiet
when both sides are physics-only.

Known risks: replays recorded on older builds may diverge from this build in
dense battles, because a collision is now re-tested when an object moves
rather than every frame -- the order of events is the same, only the timing
of the repeat test changes. Single-player behaviour is preserved where it
matters: the push-apart still runs on contact and on every real move, squish
still works while the crusher moves, and one-shot collide events are
unchanged. Pairs involving a non-physics collide object still re-test every
frame, so in an infantry-heavy pile part= may not fall all the way to
single digits -- the log will tell.

Test on device: new game on the big map, get into a big battle, watch
whether fps still collapses over the first two minutes, and send the log --
[GX-PERF-LOGIC] part= should stay in single digits in the pile instead of
climbing past 1000 ms.

## 24/11/2026 -- Branch renames and the workflow split (stable.yml / beta.yml)

The two working branches finally have short names: `custom-driver` is now
`beta`, and `stable-1.0.0` is now `stable`. Branch names carry no numbers
anymore; only release tags (`v1.0.0`) and APK file names
(`GeneralZH.v1.0.0.apk`) keep their versions.

The single shared `build-android.yml` is gone from both branches. Each
branch now carries only its own file: `stable.yml` on `stable`, `beta.yml`
on `beta`. Stable builds are triggered by pushing a tag (`v*`) -- the
version name comes from the tag, versionCode comes from
`android/app/build.gradle` (never from the tag: v1.0.0 by formula would be
10000, below the installed beta 10418, and Android would refuse it as an
update), and the tag message becomes the What's New intro. There is no
tag-move step anymore, because the tag already points at the build commit.
Beta builds are manual dispatch only, artifact only -- the release steps
are removed from `beta.yml` entirely, so a beta can never be published as a
release by mistake. Both files name their outputs by version
(`GeneralZH.v<version>.apk`, `libmain-v<version>.symbols.txt.gz`).

This commit follows the rename through the code: the language-pack URLs in
SetupActivity and the update manifest URL in UpdateManager now point at
`beta`, and the packaging script's channel messages and the publish guide
say `beta` too. The manifest itself still lives under `updates/` on that
branch; the publish scripts still target the old layout and need updating
before they are used again. Older diary entries keep the old branch names
-- they are history, not current instructions.
