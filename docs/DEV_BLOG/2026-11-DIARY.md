## 23/11/2026 -- custom Vulkan driver manager: per-GPU catalogue, in-app download, revert after failed starts

The driver card used to be Adreno-only, hidden behind the experimental Vulkan unlock, and
the only way to get a driver in was to import a zip by hand. The manager is now a real
feature: `SetupActivity` builds a card that is always visible, `GpuInfo` reads the GPU from
`GL_RENDERER` and filters a catalogue of eleven community sources by family -- Turnip builds
(ARMSX2, K11MCH1, MrPurple, Banners, Droid-Deck) and StevenMXZ Gen8 for Adreno, MaliSX2 for
Mali G31-G715, ExynosTools and MdiEx for Xclipse -- and `DriverDownload` fetches the newest
release asset from GitHub, checks its SHA-256, and installs the adrenotools-format zip. The
card shows the recommended driver for the phone and the credit line under each download
button, because these are other people's open-source work, not ours.

The safety net counts failed starts and reverts to the system driver after two. The first
version counted every launch, which punished GLES players for crashes that had nothing to
do with the driver; it now counts Vulkan launches only, and a GLES launch clears the
counter. One design note from the ARMSX2 study that shaped this: pin the driver before the
first Vulkan load, and always keep a working fallback -- the revert path is the feature,
not the download.

## 23/11/2026 -- Mali phones default to Quality upscaling; 60 Hz sim gets a warning

Two small fixes that came out of the same device session. On a Mali phone the default
upscaler was Performance (50%), which is cheaper than the phone needs; Mali now defaults
to Quality (67%) unless the player already picked a mode, seeded into `Options.ini` when
the Graphics tab is built and again on game launch. On the old Mali test phone that moved
44 to 57 fps at 75% with GSR, interface still at full resolution.

The other one is a warning, not a fix: a 60 Hz sim rate on Mali doubles the logic work on
a CPU-bound phone, and the sim-rate picker gave no hint of that. It now shows a warning
with a one-tap "Use 30 Hz" button when Mali is detected. The 9 fps report that prompted
it (sim 60 Hz, Game Speed slider at 20, bracket [40]) is the same story: 9/60 is 15% of
real-time speed, where 28/30 is 93%.

## 23/11/2026 -- Indonesian: launcher strings, in-game pack, and PR #88 upstream

Indonesian is the missing locale. The launcher strings (`values-in/strings.xml`, 495
entries, translated from the English default only -- no other locale as reference) and the
in-game pack (`languages/indonesian/`, 6,486 entries) both landed, and `indonesian` is in
`languages/index.txt`. Verification was mechanical: all 6,425 English labels present, no
duplicates, no malformed quotes, `generals.str` byte-identical to the English source.
484 entries are identical to English, all legitimately untranslatable (names, map names,
single letters, "OK", format strings), matching the German pack's convention. Faction
names and named units stay English; the player is mostly "kamu".

Two things worth remembering. First, the strings were in the APK but the language was
not pickable: the launcher picker is a hardcoded list (`LocaleHelper.SUPPORTED_TAGS`)
with no "in", so `ded7796` adds the tag, the display name "Bahasa Indonesia", and the
pack mapping. Second, the pack is downloadable in the beta without waiting for upstream:
beta builds fetch language packs from this fork's `custom-driver` branch instead of
upstream main (`b6f8a2a`), and the branch serves `index.txt` with `indonesian` listed and
the pack at HTTP 200. That change is fork-only and is not in the PR.

PR #88 to MYSOREZ ("Add Indonesian language pack", `indonesian-language-pack` off
upstream main `a520ed1b`) carries the pack, the README section, the picker fix, and a
`values-in` adapted to upstream (488 entries: the 8 driver-only strings dropped, 3
strings re-translated from upstream's English, `setup_toast_reset_auto` added). It is
open and mergeable with no conflicts. No CI runs on PRs -- the workflow is manual
dispatch only -- and the "1 workflow awaiting approval" on it is GitHub's standard
protection for fork PRs; only the maintainer can approve it, and it does not block
merging. The plan agreed for the rest: one focused PR per topic, each off upstream main
-- custom Vulkan driver next (after an upstream-compat check), then the Mali small fixes.

## 23/11/2026 -- FPS watch log, and what the first device log showed

`[gxfps]` lands in `generals-stderr.log` once every 5 s while a real game runs: drawn
fps, logic Hz, pace (game-time vs real-time), logic step, frame ms, FPS cap. It is
readable without adb from the launcher's Log Viewer. One correction followed the first
device log: a single-player game with no Sim Rate lock reports a logic rate of
1,000,000 Hz (uncapped), which made pace print as 0.00 -- reading as a frozen game when
the game was only slow. The line now prints `sim=uncapped pace=n/a` in that case
(`ce90f37`).

The first log (build 10408, Mali-G68, GLES, SGSR at 50%) confirmed the Indonesian pack
on device and showed the real problem: menus hold ~30 fps, in-game degrades
31 -> 13.6 -> 16.4 -> 11.3 -> 7.0 -> 6.3 fps. Logic is 1.1-3.9 ms/frame and pixels are
already at half resolution, so neither the sim nor the fill rate is the bottleneck. The
client is: 120-203 ms/frame, terrain 764-1044 draws/frame, ~23 MB of vertex uploads per
frame, and a 91.5 ms `preRTT` pass.

## 23/11/2026 -- driver download always failed: the credit line was read as a checksum

A device test caught it: tapping Download MaliSX2 always toasted "Checksum mismatch".
The 6-argument `DriverCatalog.Source` constructor took its last parameter as a pinned
SHA-256, so the nine sources that passed a credit line there compared every downloaded
zip against that text and always failed -- and showed no credit under their buttons.
The 6th argument is now the credit; a pinned checksum uses the 9-argument form
(`aa92761`). MaliSX2 itself has no pinned checksum by design (empty means skip the
check). The failed download changed nothing on disk, so the manually imported MaliSX2
0.6.1 was untouched. The credit line now shows on the card, which is how the fix was
confirmed on device.

## 23/11/2026 -- the in-game bottleneck is the per-frame terrain update, not the GPU

The investigation (engine thread, not GPU/sim/pixels) ranked three suspects. First,
the phase logged as `preRTT` is not the render-to-texture passes -- in
`W3DDisplay::draw()` it is `updateViews()` plus the particle update, and it grows
across the session: 91 -> 122 -> 132 -> 177 ms, while the main scene stays flat at
12-20 ms. Inside it the prime suspect is the terrain-center recompute
(`W3DView::update()` -> `updateTerrain()` -> `HeightMap::updateCenter()` ->
`updateBlock()` -> `updateVB()`): the upload volume tracks it almost exactly
(91 ms with 23 MB, 122 ms with 35 MB). Particle counts are tiny (14-16 draws), so the
particle update is unlikely to be 90 ms -- but that is an inference, not a measurement,
and the zoom-settle path (`adjustZoomWhenNotScrolling` keeping `m_recalcCamera` set)
is an unproven candidate for why it never goes quiet.

Second, plain-lock vertex uploads: 23-35 MB/frame across 173-259 uploads. The dynamic
ring buffer is innocent (DISCARD/NOOVERWRITE, 0.04 ms); the plain locks come from
`HeightMapRenderObjClass::updateVB`, which locks the whole 180 KB tile buffer per
touched tile though only a few rows changed. The attribution is not complete: 23-35 MB
is 128-192 tile-equivalents against 16-64 visible tiles, so another plain-lock user
may contribute.

Third, the 1044 terrain draws per frame are mostly a red herring: 1.3-2.7 ms of
translator time and 0.1 ms of `glDraw`. Three passes per tile is the fixed shader model
(base + noise + cloud), not a bug. Ruled out by the log: logic, pixels, water/shadow
RTT (0.00 ms in every window), UI, models/particles/decals, audio, network, present,
and GPU saturation (render worker busy 20-27 ms against 126-217 ms frames). The 1.8 fps
window partly overlapped the map-load hitch, so steady state is ~6-7 fps -- still bad.

The recommended order: (1) a diagnostic build that splits the update phase and tags
uploads by source; (2) ranged terrain VB locks (upload only the touched rows);
(3) terrain-center throttling / zoom-settle fix, guided by the diagnostic; (4) merge
the 3 terrain passes and re-run terrain LOD calibration on game start. If the update
phase drops from ~130 ms to ~20 ms that is roughly 3x fps on its own; ranged locks
should take another 20-30 ms off the frame.

Build 10409 (`bce9374`) is that diagnostic build: `[GX-PERF-DISPLAY]` gains
`updViews` and `particles`, a new `[GX-PERF-VIEW]` line reports `view` / `terrain` /
`terrainCalls` / `rest` / `centerCalls` / `blockCalls` / `blockCells` once per second,
and a new `[d3d8gles] perf-syncupload/frame by source` line splits synchronized
uploads into terrain / models / sorted / 2d-ui / other. Measurement only. The next
device log (skirmish, 1 minute or more) settles suspects 1 and 2 together.
